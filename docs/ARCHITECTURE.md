# Архитектура и стек

Документ фиксирует решения, принятые до начала разработки, и их обоснование.
Пересматривать его стоит, когда меняется что-то из раздела «Исходные данные».

## 1. Исходные данные

**Что переписываем.** [telegramdesktop/tdesktop](https://github.com/telegramdesktop/tdesktop)
(ветка `dev`, на момент старта — релиз v7.4.1, TL-слой 233):

- ~40 МБ C++ в основном репозитории плюс собственные библиотеки `lib_ui`, `lib_base`,
  `lib_rpl` (реактивность), `lib_crl` (многопоточность), `lib_tl`, `lib_storage`,
  `lib_lottie`, `lib_webrtc`, `lib_webview` и ~25 сторонних сабмодулей.
  Порядок — **сотни тысяч, скорее больше миллиона строк**.
- UI — на Qt, но почти всё рисуется вручную через `QPainter` (CPU-растеризация);
  OpenGL используется точечно (видео, звонки, некоторые анимации).
- Сеть — собственная реализация MTProto (TDLib **не** используется).
- Релизы выходят часто: 5 штук за три недели (v7.3.3 → v7.4.1), около 40–100
  коммитов между соседними версиями. Схема API меняется почти каждый месяц.

**Вывод:** полный паритет — это годы работы. Значит, нужны (1) поэтапный план с
полезным результатом на каждом шаге и (2) автоматическое отслеживание оригинала,
иначе мы будем вечно отставать. Второе уже сделано — см. [UPSTREAM.md](UPSTREAM.md).

## 2. Почему Rust — и откуда на самом деле возьмётся скорость

Rust — правильный выбор, но **не потому, что он быстрее C++**. По сырой
производительности они равны; tdesktop уже написан на хорошо оптимизированном C++.
Если просто построчно перевести код, быстрее не станет.

Rust выигрывает тем, что позволяет **безопасно** делать то, что в C++ слишком
рискованно на кодовой базе такого размера:

| Где tdesktop теряет скорость | Что делаем мы |
|---|---|
| Почти весь UI растеризуется на CPU (`QPainter`) | Рендеринг целиком на GPU: текст, тени, blur, скругления, анимации |
| Основная логика и обработка апдейтов в главном потоке | Главный поток только раскладывает и рисует; разбор апдейтов, БД, декодирование — в рабочих потоках. Rust гарантирует отсутствие гонок на этапе компиляции |
| `QString` (UTF-16) и копирование данных между слоями | UTF-8 везде, разбор TL без копирования (`&[u8]`/`Bytes`), неизменяемые снапшоты состояния через `Arc` |
| Самописный зашифрованный формат `tdata`, многое держится в памяти | SQLite (WAL) + файловый кэш с лимитами: быстрый холодный старт, низкое потребление RAM, локальный полнотекстовый поиск |
| Медиа декодируется в основном программно | Аппаратное декодирование (D3D11VA / VideoToolbox / VAAPI), параллельная подготовка превью через `rayon` |

Альтернативы: C++ — не даёт выигрыша; Zig — незрелая экосистема для GUI;
Go / C# / Java — сборщик мусора даёт паузы при скролле; Electron/Web — заведомо медленнее.

### Бюджеты производительности

«Самый быстрый» должен быть измеримым. Целевые показатели (на средней машине,
сравниваем с tdesktop той же версии на тех же аккаунтах):

| Метрика | Цель |
|---|---|
| Холодный старт до первого кадра со списком чатов (из кэша) | < 300 мс |
| Открытие чата из кэша | < 1 кадра (≤ 8 мс при 120 Гц) |
| Скролл ленты с медиа | стабильно на частоте монитора, без пропуска кадров |
| RAM в простое, 1 аккаунт | в 2+ раза меньше tdesktop |
| Размер установщика | меньше tdesktop |

Бенчмарки (`criterion`) и замеры (`tracing` + Tracy) появляются вместе с кодом,
регрессии ловятся в CI.

## 3. Юридические рамки (важно сделать сразу)

1. **Лицензия — GPLv3.** Порт кода tdesktop — производная работа от GPLv3-кода,
   поэтому проект распространяется под GPL-3.0-or-later (файл `LICENSE` уже добавлен).
   Это позволяет свободно переиспользовать алгоритмы, строки локализации, иконки и
   стили tdesktop. Код под Apache-2.0/MIT (например, grammers) совместим с GPLv3.
2. **Свой `api_id` / `api_hash`** с [my.telegram.org](https://my.telegram.org) — получены.
   В репозиторий ключи не коммитим: локально они лежат в `.env` (в `.gitignore`,
   шаблон — `.env.example`), в CI берутся из секретов `TDR_API_ID` / `TDR_API_HASH`.
3. **Правила Telegram API** ([Terms of Service](https://core.telegram.org/api/terms)) —
   что из них следует для нас:
   - п. 2.3: в названии нельзя использовать «Telegram», если перед ним не стоит
     «Unofficial». Отсюда название продукта — **Unofficial Telegram Desktop Rust**;
   - п. 2.4: официальный логотип использовать нельзя, нужна своя иконка. Это
     единственное место, где мы визуально отличаемся от оригинала;
   - п. 2.2: в интро при первом запуске нужно указать, что приложение работает
     через Telegram API;
   - п. 3.3: спонсорские сообщения в каналах должны поддерживаться и работать как
     в оригинале;
   - п. 1.4: никаких «режимов призрака»: статусы «прочитано», «печатает» и
     «в сети» работают честно.
4. Соблюдать [security guidelines](https://core.telegram.org/mtproto/security_guidelines)
   MTProto — проверки `msg_id`, `msg_key`, параметров DH и т.д.

## 4. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Rust stable, edition 2024 | — |
| Асинхронность | `tokio` для сети и диска | Стандарт де-факто, IOCP на Windows |
| CPU-параллелизм | `rayon` | Декодирование превью, blur, поиск |
| TL-кодогенерация | **свой** `tdr-tl-gen` (на базе `tdr-tl-parser`) | Полный контроль над zero-copy разбором; схема обновляется автоматически из upstream |
| MTProto | **свой** `tdr-mtproto`, идеи и куски кода из [grammers](https://codeberg.org/Lonami/grammers) | Нужны вещи, которых нет в готовых библиотеках: отдельные сессии на загрузку/выгрузку, CDN-DC, временные ключи (PFS), MTProxy, тонкая работа с апдейтами как в tdesktop |
| Криптография | RustCrypto (`aes` с AES-NI, `sha1`, `sha2`), IGE поверх блочного шифра; big-int для DH/RSA | Аппаратное ускорение без C-зависимостей |
| Хранилище | SQLite (`rusqlite`, bundled, WAL, FTS5) + файловый кэш с LRU-лимитами; шифрование локальных данных при включённом код-пароле | Зрелость, мгновенный старт, локальный поиск |
| UI | **GPUI** (см. §5) | GPU-рендеринг, проверен в Zed |
| Текст | системные шейперы через GPUI (DirectWrite / CoreText / cosmic-text) | bidi, лигатуры, emoji, IME |
| Видео/аудио | FFmpeg через `rsmpeg`/`ffmpeg-sys-next`, аппаратное декодирование; звук — `cpal` + `opus` | Переписывать кодеки на Rust бессмысленно |
| Изображения | `zune-jpeg`, `png`, `libwebp`, AVIF/HEIF позже | Скорость |
| Lottie (TGS) | сравнить `rlottie` (FFI, как в tdesktop) и `velato` (Rust, GPU) | Решаем бенчмарком на этапе 4 |
| Звонки | `tgcalls` + WebRTC через C-ABI обёртку | Переписывать WebRTC нереально; поздний этап |
| Mini Apps | системный WebView (`wry`) | Как и в tdesktop |
| Аллокатор, логи | `mimalloc`; `tracing` + Tracy | — |

## 5. UI-фреймворк — главное решение

Требования мессенджера: виртуализированная лента на десятки тысяч сообщений разной
высоты, сложный текст (bidi, entities, inline анимированные custom emoji, спойлеры),
анимации 120+ Гц, blur и кастомные эффекты, IME, трей, уведомления, accessibility.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **GPUI** (Zed, Apache-2.0) | GPU (DirectX 11 / Metal / Vulkan); доказанная скорость на огромных объёмах текста; списки с переменной высотой; IME; гибридная модель (retained + immediate) | API заточен под Zed и меняется; мало документации; accessibility пока слабая |
| Slint | Декларативный язык, хорошие инструменты, GPL-совместим | Сложный кастомный рендер ленты чата неудобен; рендереры femtovg/skia |
| iced | Чистая Elm-архитектура, wgpu | Производительность больших списков и текста ниже |
| egui | Очень просто начать | Immediate mode: перерисовка всего кадра, плохо для батареи и сложного текста |
| Свой: `winit` + `wgpu` + `vello` + `parley` | Максимальный контроль, потенциально самый быстрый | +6–12 месяцев до первого полезного экрана, всё (IME, a11y, скролл, фокус) делать самим |

**Решение (принято):** GPUI. При этом UI отделён жёсткой границей: всё состояние живёт в
`tdr-data`, UI только подписывается на него и рисует. Если GPUI упрётся в потолок —
меняется только слой `tdr-ui`/`tdr-app`, а не протокол и данные.

### Визуальная идентичность с оригиналом

Цель — клиент, который выглядит и ведёт себя как tdesktop. Чтобы не перерисовывать
интерфейс «на глаз» и не отставать от редизайнов, всё берём из исходников оригинала
автоматически:

- **Стили.** В tdesktop все размеры, отступы, шрифты, иконки и анимации описаны в
  декларативных файлах `*.style`, а цвета — в `colors.palette`. Генератор
  `tdr-style-gen` будет переводить их в Rust-константы, так же как TL-схему. Тогда
  изменение стиля в оригинале автоматически приходит к нам через трекер upstream.
- **Иконки и ресурсы** (кроме логотипа) копируются из `Telegram/Resources`.
- **Тексты** — из `lang.strings`, включая правила множественного числа.
- **Поведение** (анимации, тайминги, жесты) переносим из кода по коду, сверяя видео
  оригинала и порта кадр за кадром.

## 5a. Оптимизация решений самого оригинала

Кроме смены стека, ищем неоптимальные места в коде tdesktop. Порядок такой:
перед переносом каждой подсистемы профилируем её в оригинале и изучаем код, находки
и решения записываем в [OPTIMIZATIONS.md](OPTIMIZATIONS.md). Улучшение принимается,
только если подтверждено замером и не меняет видимого поведения.

## 6. Структура crates

```
tdr-tl-parser   ✅  парсер и differ TL-схем (используется трекером upstream)
tdr-tl-gen      ✅  генерация Rust-типов из schema/*.tl (build.rs)
tdr-tl          ✅  сгенерированные типы и (де)сериализация без копирования
tdr-crypto      ✅  AES-IGE, MTProto 2.0, RSA_PAD, DH, SRP (2FA)
tdr-mtproto     ✅  обфусцированный транспорт, создание ключа, сессия, контейнеры, ack/resend
tdr-api         ✅  ядро клиента: несколько DC, временные ключи (PFS), перенос авторизации,
                    *_MIGRATE, FLOOD_WAIT, сохранение сессии
tdr-cli         ✅  консольный клиент для проверки стека (вход по QR/номеру, чаты, файлы, самотесты)
tdr-api             запросы, очередь, flood-wait, апдейты (pts/qts/seq, getDifference)
tdr-data            доменная модель: пиры, история, сообщения, стикеры; снапшоты для UI
tdr-storage         SQLite, файловый кэш, шифрование
tdr-media           декодеры изображений/видео/аудио, плееры, lottie
tdr-lang            локализация (формат lang.strings из tdesktop)
tdr-ui              тема, базовые виджеты, анимации поверх GPUI
tdr-platform        трей, уведомления, автозапуск, интеграция с ОС
tdr-app             экраны: вход, чаты, лента, профили, настройки… (бинарник)
xtask           ✅  автоматизация: отслеживание upstream
```

Модель потоков: сеть и диск — `tokio`; состояние меняет один «писатель» (actor),
который применяет апдейты и публикует неизменяемые снапшоты; UI-поток только читает
снапшоты — без блокировок на пути отрисовки.
