# Журнал оптимизаций

Здесь копятся найденные в оригинальном tdesktop неоптимальные решения и то, как
мы их решаем. Правила:

- Утверждение «в оригинале медленно» записывается сначала как **гипотеза**.
  В **подтверждённые** оно переходит только после замера (профайлер, бенчмарк,
  ссылка на конкретный код в tdesktop).
- Улучшение не должно менять видимое поведение клиента.
- У каждой записи есть ссылка на код в tdesktop и, после реализации, — на наш код и
  результат замера.

## Подтверждено

| # | Где в tdesktop | Находка | Что сделали мы |
|---|---|---|---|
| C1 | `mtproto/mtproto_dh_utils.cpp`, `IsPrimeAndGood` | Для известного простого числа Telegram при `g = 2` и `g = 6` каждый раз заново запускаются две проверки простоты 2048-битных чисел, хотя число заранее известно как безопасное простое | Для известного простого — только дешёвая проверка остатка по модулю для `g` (`tdr-crypto/src/dh.rs`). Тест подтверждает, что константа — безопасное простое |
| C2 | там же | Для известного простого `g ∈ {3,4,5,7}` принимается **без проверки** условия на `g`. Для `g = 5` оно не выполняется (p mod 5 = 3), то есть клиент принял бы неподходящий генератор. Серверы присылают `g = 3`, поэтому на практике это не проявляется | Условие на `g` проверяется всегда (тест `known_prime_needs_a_proper_g`) |
| C3 | `mtproto/session_private.cpp`, `mtproto/details/mtproto_dcenter.cpp`, `mtp_instance.cpp` (`getKeysForWrite`) | Временные ключи (PFS, срок 24 ч) живут только в памяти: при **каждом запуске** заново идёт DH с сервером для каждого нужного DC. По нашим замерам это ≈ 1,1–1,3 с до первого ответа | Опция `persist_temp_keys`: ключ сохраняется вместе с постоянным и переиспользуется, пока ему осталось больше 5 минут. Старт → ответ: **≈ 120–170 мс вместо ≈ 1200 мс**. Компромисс описан ниже |
| C4 | там же | Соль сервера после запуска неизвестна, поэтому первый запрос всегда получает `bad_server_salt` и уходит повторно (+1 круг) | Соль сохраняется вместе с временным ключом: повторов при старте больше нет |
| C5 | `mtproto/` | Ключ и авторизация для «медийного» DC создаются в момент первой загрузки файла (гипотеза H8) | `Client::prepare_dc` — подготовка соединения в фоне. Первый запрос к DC 4 после запуска: **1117 мс → 139 мс** |

### Компромисс C3: сохранение временных ключей

PFS защищает старый перехваченный трафик, если позже утечёт постоянный ключ. Если
временный ключ лежит на диске рядом с постоянным, то при краже данных с устройства
можно расшифровать перехваченный трафик за последние ≤ 24 часа (время жизни ключа).
Без сохранения — нельзя. Доступ к самому аккаунту вор получает в обоих случаях:
постоянный ключ и так хранится на диске.

**Решение (2026-11-10): сохранять по умолчанию** — скорость важнее. Опция
`Config::persist_temp_keys` позволяет вернуть поведение tdesktop. Когда появится
локальный код-пароль, временные ключи будут зашифрованы вместе с остальной сессией.

## Замеры

Release-сборка, подключение к DC2 (сетевая задержка ≈ 65 мс):

| Операция | Время | Комментарий |
|---|---|---|
| Создание ключа авторизации | ≈ 1,1–1,5 с | Наш CPU ≈ 40 мс; остальное — 4 круга по сети и вычисления DH на сервере (0,5–0,7 с на шаг) |
| Первый запрос (`initConnection`) | ≈ 70–90 мс | ≈ 1 круг |
| 20 параллельных запросов | ≈ 84 мс | Упаковываются в один контейнер, то есть 1 круг вместо 20 (последовательно ≈ 1,6 с) |
| Запуск → первый ответ, как в tdesktop (новый временный ключ) | ≈ 1200 мс | Вход уже выполнен; TCP + DH + привязка + `initConnection` |
| Запуск → первый ответ, сохранённые ключ и соль | ≈ 120–170 мс | TCP + 1 круг |
| Первое обращение к новому DC | ≈ 2,6 с | Разово: постоянный + временный ключ, привязка, экспорт/импорт авторизации |
| Обрыв соединения посреди 10 запросов | ≈ 120–145 мс | Переподключение + повтор с теми же msg_id, все 10 ответов получены |

## Гипотезы (проверить профайлером)

| # | Где | Гипотеза | Что предлагаем |
|---|---|---|---|
| H1 | `lib_ui` | Растеризация интерфейса на CPU через `QPainter` даёт основную нагрузку при скролле и анимациях | Всё рисовать на GPU (GPUI) |
| H2 | Обработка апдейтов | Разбор и применение апдейтов в главном потоке вызывает подлагивания при всплесках (большие группы, переподключение) | Разбор и применение в фоновом actor, в UI уходят готовые снапшоты |
| H3 | `storage/` (`tdata`) | Самописный зашифрованный формат читается при старте крупными кусками | SQLite (WAL) с ленивой загрузкой, только видимое на первом экране |
| H4 | Строки | Конвертация UTF-8 (сеть) → UTF-16 (`QString`) → UTF-8 на каждом сообщении | UTF-8 от сети до шейпера |
| H5 | Медиа-кэш | Превью и стикеры держатся в памяти как развёрнутые `QImage` | GPU-текстуры + сжатый кэш на диске, лимиты по памяти |
| H6 | Сериализация TL | Ответы копируются в промежуточные структуры | Разбор без копирования: `bytes` — срезы исходного буфера (`Bytes`) |
| H7 | Анимированные стикеры/эмодзи | Декодирование Lottie на CPU для каждого видимого экземпляра | Общий кэш кадров на экземпляр стикера, рендер на GPU (`velato`) — сравнить |

## Сделано в порте

| Где | Что | Эффект |
|---|---|---|
| `tdr-tl` | Поля `bytes` — `Bytes` (общий буфер со счётчиком ссылок), а не копия | Нет копирования файлов и медиа при разборе ответов |
| `tdr-tl` | Крупные конструкторы хранятся в `Box`, мелкие (только примитивы, ≤ 16 байт: `peerUser`, `inputPeerChannel`…) — прямо в `enum` | `Message`, `Update`, `InputPeer` ≤ 24 байт (проверяется тестом), а пиры не требуют выделений памяти |
| `tdr-mtproto` | Все запросы, накопившиеся за время записи в сокет, вместе с подтверждениями (acks) уходят одним контейнером | 20 запросов — 1 сетевой круг |
| `tdr-mtproto` | Чтение сокета — в отдельной задаче, без `select!` | Кадры не теряются при отмене, нет лишних копий |
